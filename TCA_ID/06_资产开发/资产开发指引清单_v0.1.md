### 1.2 分工

| 参与者 | 职责 |
|---|---|
| 用户 | 表达偏好，比较候选，确认风格、角色设计、生产范围与成品 |
| dsh＋DeepSeek | 读取上下文、拆问题、给出有理由的建议、编写生成任务、协助制作与整理、检查结果、记录进度 |
| gptimage2.5、googlenanobanana | 按用户实际可用能力执行图片生成／编辑；由用户选择和操作，或在用户明确授权且工具可用时接入 |
| 绘画／建模／动画工具与操作者 | 完成分层修整、建模、材质、骨骼、动画及导出；具体工具按路线决定 |
| Godot 工程操作者 | 在获准的工程中完成导入、组装、交互、实际画面与性能验证 |

不要根据模型名称宣称支持透明背景、多图参考、固定种子、精确尺寸、分层、批量生成或商业授权。先查用户可用界面／官方说明，缺少的能力采用人工处理或替代步骤。

### 1.3 每轮怎样带用户推进

- 每轮聚焦一个主要决定，通常给 2～3 个可比较选项，并说明推荐理由、工作量和影响。
- 问偏好时用画面特征与例子，避免只问“喜欢什么风格”。必要时请用户提供参考图。
- 用户已确认的决定不要反复询问。文件检查、登记、可回退整理等已授权工作继续推进。
- 每轮输出：当前阶段、已知依据、本轮建议／问题、已完成文件、待办和下一步。
- 用户说“都行”时，记录原话和采用的建议范围；不要据此扩展为对全部角色、所有地区或技术参数的批准。
- 不以低完成度占位内容代替完整交付。先做范围可控、达到目标品质的完整样板，再扩展产量。
- 遇到阻塞，记录依赖并继续不依赖该决定的工作；规则未定不妨碍比较画风，但不能制作冒充正式内容的卡牌。
- 对话结束前更新进度和台账。没有文件写入能力时，输出可直接保存的完整内容，并注明尚未落盘。

## 2．当前项目边界

| 事项 | 当前依据 |
|---|---|
| 探索方向 | 参考用户视频的斜俯视与场景观感；不是已确认的严格等距、45° 或固定投影 |
| 场景观感 | 简化几何、体积与遮挡、柔和自然配色、氛围光影是参考分析，具体参数待定 |
| 人物方向 | 用户选 B，但“二次元”没有可执行定义；不能默认头身比、五官、描边或赛璐璐着色 |
| 战斗 | 当前仍为横版 2D 目标；探索参考不自动改变战斗表现 |
| 制作路线 | 2D、3D、混合待评估；3D 场景只是此前建议 |
| 角色内容 | 14 名可玩角色是规划规模，正式名单和首个测试角色仍待定 |
| 科学内容 | 元素、化学式、配方与效果以正式内容和审核台账为准；图片生成不能充当科学审查 |
| 工程边界 | 当前目录是设计工作区，不放 Godot 代码；旧 Godot 工程暂不改动 |

工作中继续使用〔确认〕〔推导〕〔待定〕〔建议〕〔目标〕标记。流程完成与美术批准是两回事。

| 阶段 | 核心产物 | 进入下一阶段的条件 |

| D 生产规划 | 分用途资产清单、规格、依赖、优先级 | 首套样板所需资源已完整拆分 |

## 4．阶段 A：先把工作条件弄清楚

- [ ] 确认 dsh 的实际使用方式：能否读写本地文件、看图、调用工具、操作 Godot；不预设它的含义与权限。
- [ ] 确认用户希望亲手完成、由 AI 辅助、委托或采购的环节，以及可投入时间和预算。
- [ ] 确认目标屏幕、窗口尺寸、目标设备与性能预期；未知时先记待定，勿编出正式预算。
- [ ] 确认可用的绘画、建模、动画工具与经验。缺少建模能力时把它列入路线成本。
- [ ] 建立参考索引：文件／链接、来源、喜欢的具体部分、不采用的部分、可否作为发布素材。
- [ ] 区分“只作风格参考”和“实际使用素材”；记录采购或授权凭据，来源不明保留待核验。
- [ ] 检查用户视频截图，描述实际观察到的特征，不推断原作引擎和制作方法。

出口：建立启动记录；仅在缺口妨碍当前选择时提问，不要求用户一次填写整张问卷。

## 5．阶段 B：把风格标签变成能执行的标准

### B1 人物

- [ ] 逐项讨论：整体比例、头脸与五官、轮廓、服装层次、细节密度、线条、材质、明暗与动画气质。
- [ ] 决定元素身份如何被识别：轮廓、配色、纹样、道具或符号；这些均先作为候选。
- [ ] 先使用同一临时角色比较，若正式角色未定，注明“仅验证风格、不进入正式名单”。
- [ ] 将人物缩到实际地图和战斗尺寸查看，不能只看放大的插画。

### B2 场景与镜头

- [ ] 比较相机俯角、透视／正交、远近和人物占屏比例，固定其他变量。
- [ ] 讨论形体复杂度、边缘处理、色板、阴影、雾感与地面材质；不顺带加入昼夜天气系统。
- [ ] 明确场景主题需要另行确认；参考视频里的棚屋、羊群、草原不自动成为 TCA 内容。
- [ ] 对比前景遮挡、建筑与角色比例、可行走空间、交互物识别。

### B3 战斗、卡牌与整体一致性

- [ ] 在横版战斗构图中查看同一人物，明确与探索人物共享哪些设计、另做哪些资源。
- [ ] 讨论卡牌、HUD 和场景之间的色彩与形状联系；确定信息优先级后再装饰。
- [ ] 剧情立绘、表情差分、配音均单独决定是否需要。

### B4 对比与确认方法

- [ ] 每轮 2～3 个候选，保持相同人物、姿态、构图、背景和展示尺寸，只改变主要待比较因素。
- [ ] 图片标注候选 ID、生成来源、变化项；生成工具无法严格控制变量时注明比较局限。
- [ ] 收集“保留什么／改变什么／无法判断什么”，记录到具体候选和版本。
- [ ] 形成《美术风格规范》：参考索引、人物／场景／战斗／UI 规则、正反例、配色、禁止偏移、未决项。

出口：用户确认的是明确特征与样稿版本。选中一张图不自动批准图片中的所有偶然细节。

## 6．阶段 C：选择并验证技术路线

- [ ] 比较：3D 场景＋3D 人物、3D 场景＋2D 人物、2D 预渲染；也可加入用户提出的路线。
- [ ] 比较镜头自由度、方向数量、动画、遮挡、光影统一、修改成本、所需技能和后续角色扩展。
- [ ] 画清同一角色的复用关系：探索模型／图片、战斗角色、头像、卡图与可能的立绘。
- [ ] 3D 候选验证尺度、材质、骨骼、动画与导出；Blender 的复杂材质不能默认与 Godot 一致。
- [ ] 2D 候选验证所需方向、转身、翻转限制、透明边缘、脚底接地、遮挡与动画一致性。
- [ ] 预渲染候选验证相机锁定、投影一致、地面接缝、阴影和方向变化需要的额外素材。
- [ ] 在获准的独立测试工程中使用目标 Godot 版本验证；先确认工程路径，不改旧工程。
- [ ] 保存同镜头截图、问题、实际操作步骤和结果。无引擎条件时只标记“概念通过／技术待验”。

出口：路线决定附证据与限制；不以概念图替代引擎验证。具体接口、格式和导入操作以目标版本官方文档为准。

## 7．阶段 D：建立资产生产计划与规格

### D1 覆盖范围

- [ ] 探索：人物、地面与模块、建筑、装饰、交互物、遮挡处理所需资源。
- [ ] 战斗：双方角色、背景、所需动作、目标／受击反馈、终局表现；敌人名单待正式内容确认。
- [ ] 卡牌：通用框架、不同类型的视觉区别、插画、头像、元素及资源标识。
- [ ] UI：主流程所需界面、按钮状态、面板、字体、鼠标／键盘／手柄提示中实际需要的部分。
- [ ] 特效：出牌、合成、攻击、受击及已批准状态；不为未定机制生产正式效果。
- [ ] 声音协作：为画面标出需要配音效的事件和时间点，音乐音效单独登记；本轮美术任务不默认扩展为完整音频制作。

### D2 每项规格

- [ ] 分配稳定资产 ID、用途、关联角色／卡牌／场景、依赖和优先级。
- [ ] 2D：画布、最终显示大小、透明要求、边距、锚点、色彩空间、导出格式、缩放方式。
- [ ] 3D：单位、朝向、原点、尺寸、材质与贴图约定、碰撞范围、导出格式；面数和贴图预算通过样板测量后确定。
- [ ] 动画：状态、方向、时长、循环、过渡和事件点；逐帧方案另定帧数／帧率，骨骼方案另定绑定规范。
- [ ] UI：布局、文字与图分离、适配与切片、悬停／按下／禁用／焦点等适用状态。
- [ ] 特效：开始／峰值／结束、持续时间、挂点、遮挡层级、画面占比、声音事件点。
- [ ] 写明验收证据、源文件交付要求和授权状态。

出口：完整拆分首套样板，再估算整批数量。分别计算独有资源、可复用资源、方向／动作变体和外部制作工作；不把“14 个角色”当成“14 张图片”。

## 8．阶段 E：制作一套达到目标品质的完整样板

建议范围由用户确认，不直接当作已批准内容：

- [ ] 一个元素角色，正式角色未定时使用明确标注的临时设计。
- [ ] 一个能检查行走、遮挡与交互的小型探索场景。
- [ ] 同角色的横版战斗表现，以及用于验证交战反馈的对手。
- [ ] 覆盖实际需要的代表卡牌类型、资源标识和合成界面。
- [ ] 一次能验证完整视觉反馈的合成／出牌过程；正式配方未审核时只能作为视觉演示。
- [ ] 路线所需的动作与方向，逐项来自已确认的需求，而不是默认套用动画数量。
- [ ] 角色、场景、卡牌、界面、特效在同一真实显示尺寸下检查。
- [ ] 按下一节的图片工作流生产，再按第 11 节验收。

出口：用户确认视觉品质；技术验收另有记录；记录单项耗时、修改轮次、返工原因和复用收益，作为后续估算依据。

## 9．图片生成与编辑的单项工作流

1. **立任务。** 使用任务模板，先写用途与验收条件，再编提示词。资产台账置为“制作中”。
2. **准备参考。** 分清角色身份参考、风格参考、构图参考、色彩参考；列明优先关系和不能改变的特征。
3. **选择工具。** 根据用户可用能力选择 gptimage2.5 或 googlenanobanana。比较模型时采用相同任务，不预设谁负责哪类成品。
4. **生成候选。** 候选编号与版本可追溯；保存提示词、参考文件、设置和原始输出。界面未提供的设置记“不可用”，不虚构种子或参数。
5. **检查并反馈。** 指出具体位置和问题，例如“缩小后元素徽记无法辨认”，避免只说“不够精致”。
6. **定向修改。** 优先基于选中的版本编辑，列明保留项和变化项；工具无法保留时记录偏移并重新检查。
7. **人工／工具整理。** 按需修边、去背景、统一画布、锚点、切图与导出；先检查 alpha，白底或棋盘格不代表真实透明。
8. **使用检查。** 放到实际背景、实际尺寸和相邻资产旁检查；动画按播放检查，不以单帧批准整段。
9. **归档。** 原始输出、可编辑文件、导出文件、验收记录分别保存；登记状态和路径。

图片质量检查：

- [ ] 角色身份与已确认设计一致；跨视角、跨动作的服装、配件和颜色连续。
- [ ] 没有多余肢体、断裂、穿插、错位、意外文字、水印或裁切。
- [ ] 多视图仅作为设计参考，不能声称天然几何一致或已经是可用 3D 模型。
- [ ] 图片未天然提供绘画分层、骨骼、碰撞、可用拓扑或可播放动画；所需后续工序已落实。
- [ ] 卡牌名称、化学式、数字和规则正文由排版／Godot 文字组件承载；生成图中的字不能直接当正式信息。
- [ ] 特效视觉隐喻不冒充真实实验表现；元素符号与科学内容按正式资料复核。
- [ ] 保存来源与使用条件；可参考某画面的特征，不意味着可以直接发布其中素材。

出口：单张图片通过不等于整项资产完成；还需满足分层、动画或引擎接入等该任务要求。

## 10．阶段 F：按依赖批量生产

- [ ] 从样板提取共用色板、模型模块、材质、卡框、图标网格、骨骼或动画规范。
- [ ] 按“共用基础 → 一组配套内容 → 组内验收 → 下一组”排期；避免先生成大量彼此不匹配的散图。
- [ ] 每批只生产已确认范围，正式内容未定的资源保留为候选，不提前套上正式角色 ID。
- [ ] 每批保留与样板的对照图，检查人物比例、色彩、阴影、线条、细节密度和信息层级是否漂移。
- [ ] 变更共用规范时列出引用资产，先做兼容检查，再替换通过验收的版本。
- [ ] 记录计划／实际耗时、失败原因和剩余外部工作；据此调整下一批规模。

## 11．Godot 接入和最终验收

只有用户确认工程位置和操作范围后才修改工程；现有设计工作区保持无 Godot 代码。

- [ ] 使用目标工程实际 Godot 版本验证导入；记录原文件、导出文件、导入设置与运行版本。
- [ ] 3D 推荐先评估 glTF／GLB；检查尺寸、轴向、材质、透明、阴影、骨骼、动画循环和挂点。
- [ ] 2D 检查压缩、过滤、必要的 mipmap、透明边缘、切图、缩放与锚点；设置由资产用途决定。
- [ ] 将导入模型／图片与游戏交互封装成可复用场景，保持后续源资产重新导入不会丢失游戏配置。
- [ ] 检查碰撞、脚底、地面接触、排序、前景遮挡、提示位置和镜头边缘。
- [ ] 检查动画过渡、命中时点、特效挂点和声音同步；动画展示不得悄悄定义新战斗规则。
- [ ] 检查卡牌在手牌大小下的文字与符号、长中文名称、界面缩放、输入焦点和不同状态。
- [ ] 元素／状态识别同时使用轮廓、符号或文字，避免仅凭颜色区分。
- [ ] 在目标设备上检查资源加载、帧时间、内存与贴图占用；没有设备或预算时记“待测”。
- [ ] 导出可运行包，在工程编辑器之外检查资源缺失、字体、材质和动画。
- [ ] 修改一个源资产并重新导入，验证更新流程和已有场景引用可用。
- [ ] 保存证据：截图／录像、版本、测试条件、检查项结果和遗留问题。

验收分别记录“视觉、技术、内容、来源”四项，未满足的不能写通过。截图不能证明帧率，静态图不能证明动画或交互。

## 14．第一次实际执行应做什么

1. 读取第 1.1 节文件，确认当前边界。
2. 确认 dsh 的可操作范围和用户现有绘画／建模工具，登记未知项。
3. 向用户展示“人物外观具体化”的 2～3 种比较办法，例如用户选参考、同角色比例对比、同角色着色对比；说明建议先比较哪项。
4. 只围绕首个主要变量编写图片任务，交给用户选择的生成工具执行。
5. 收到结果后逐张编号、比较、收集选择并落盘，继续下一项风格决定。

第一次执行不批量生成 14 人，不决定正式角色名单，也不改动旧 Godot 工程。
