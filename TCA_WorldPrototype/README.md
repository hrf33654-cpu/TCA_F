本文确定探索子项目要验证什么、设计从何而来以及怎样与战斗衔接。它不扩大 Prototype 0 的战斗范围，不代表正式世界生产立项或技术路线已经验收。

## 1. 本项目要做什么

制作一个可独立运行的小型探索样板：玩家能在具有斜视空间感的场景里移动、观察、发生基础互动，并通过测试敌人进入战斗后返回。

重点验证像素角色、场景空间、光影、镜头与操作能否共同产生旅行氛围和清楚的空间关系。样板应具有代表性和完整体验，不依靠空地图上的移动证明探索已经成立；也不扩展成完整城镇或大地图生产。

## 3. 首轮样板范围

| 内容 | 首轮要做到什么 | 边界 |
|---|---|---|
| 场景空间 | 一块小而完整的区域，具备可行走地面、建筑或体块、前后层次及醒目目标点 | 主题与摆放属于实验内容，不设定正式世界观 |
| 角色 | 使用氧的身份参考，建立清晰尺度和移动反馈 | 可先用标明用途的占位 Sprite；不能把静态设定图当成已完成的方向动画 |
| 镜头 | 固定斜视镜头为首轮方案，比较空间可读性和角色尺度 | 正交／透视、精确角度、景深、跟随仍需试验，不预设必须精确 45° |
| 移动与碰撞 | 完整键鼠移动路径、合理碰撞，不穿墙、不被装饰物无故卡住 | 移速与碰撞尺寸为可调测试参数 |
| 遮挡 | 角色经过前景或建筑附近时仍能判断位置和通路 | 淡出、轮廓或场景构图方案按实测选择 |
| 光影与氛围 | 对比受控的光照、阴影及必要后处理，保持像素角色可辨识 | 不以开启全部高级效果代替视觉设计 |
| 引导与互动 | 一个可读的阶段目标、一个调查／交互点及明确反馈 | 演示文字不作为正式剧情；交互不是正式化学机关审批 |
| 遭遇 | 一个可见测试敌人，接触后发出战斗请求 | 首轮无需敌人 AI、正式奖励或复杂遭遇系统 |
| 返回 | 战斗结束回到进入前的位置与朝向，避免立即重复触发 | 属于整合试验，不定案正式败北／检查点规则 |

探索阶段得到的是知识或线索；不能自动写成“正式配方已发现”。正式发现仍以成功合成生成产物为准。

## 4. 推荐技术基础

- 统一 Godot 4.6.2 stable、GDScript、Forward+，与战斗项目一致。
- 首轮用 Node3D 场景、3D 地面／体块、2D Sprite 角色与 Camera3D 探索混合表现；角色具体节点与朝向方案通过样板决定。
- 先稳定镜头、人物比例与移动，再逐步加入光影、景深和环境细节；每次能判断画面改善及性能代价。
- 像素角色采用适合像素资产的采样设置；3D 地面与材质独立处理，不将全项目材质统一设成像素采样。
- 不能因战斗是 2D，就让探索角色像素密度与卡牌文字共用一套未经验证的缩放参数。记录角色原始尺寸、显示尺寸、镜头距离与窗口尺寸。
- 开发时确认实际使用 RTX 4060；优先在 1280×720 和 1920×1080 下检查可读性与性能。这是测试窗口，不是最终输出规格批准。
- 60 FPS 是目标；记录实际帧时间、内存和场景规模后再判断，不能把本机流畅视为最低配置验收。

本机检查依据（2026-10-25）：i7-14650HX、RTX 4060 Laptop 8GB、16GB RAM，Godot 4.6.2 已可执行。检查时 C 盘约余 4.4GB、可用内存约 1.6GB，因此编辑器与美术工具按需开启，注意缓存空间。数据是一次快照，不是永久硬件预算；本项目不自动清理磁盘或修改系统设置。

## 5. 分阶段成果与完成标准

| 阶段 | 成果 | 完成标准 |
|---|---|---|
| W1 空间与操作样板 | 地面、体块、角色、镜头、碰撞与移动 | 连续操作不穿模、不明显卡住，角色尺度及路径可读；可独立启动 |
| W2 代表性视觉与互动 | 前后景、光影、遮挡处理、阶段目标和一个交互点 | 角色和场景协调，目标能被识别，关键路径不被景深或遮挡破坏；保存截图与参数对照 |
| W3 首次战斗接通 | 测试遭遇入口、战斗结果接收、返回上下文 | 接触→进入战斗→结束→返回原位置；连续往返不重复结算、不立即再次遇敌 |
| W4 路线复核 | 可重复运行的探索样板与测试记录 | 比较画面、操控、资产制作成本及性能，决定保留／调整技术路线，列出正式制作前缺口 |

W3 可在 W1 与战斗 M1 完成后提前进行，无需等待 W2 全部美术打磨。战斗尚未具备存档时，先测流程；战斗 M3 后补测跨场景新增发现保存。

验收主要通过实际运行、截图／录屏和性能记录。重点包括斜向移动、建筑边缘、前景遮挡、不同窗口尺寸、场景反复切换及返回触发保护。没有运行证据的项目标为未验证。

## 6. 资产来源与使用边界

- 人物身份默认参照[氧角色初始版本](../TCA_ID/02_角色/氧_角色初始版本_v1.0.md)，[氧素版](../TCA_ID/02_角色/氧_角色美术基准_素版_v1.0.md)作辅助参考。
- 像素人物及动作候选从 `../TCA_ID/06_资产开发/` 的任务、资产台账和验收记录查找；候选文件存在不等于已批准或可直接生产使用。
- 样板所用场景模型、贴图、字体和音效记录来源、许可与修改情况；开发占位和正式采用分开标识。
- 镜头和场景参考不能自动覆盖已获批人物身份；像素化和方向动作仍需单独检查一致性。
- 正式场景主题、地图布局、动画方向数／尺寸和批量生产规格，在样板验证后再决定。

## 7. 模块组织与整合约定

- 探索专属场景、脚本、材质、图像与音效组织在 `res://world/` 下，迁入主项目保持路径。
- 独立启动、实验参数和开发面板放 `res://prototype/`，正式模块不依赖测试全局对象。
- Git 管理源码、资源、配置及相关 `.uid` 文件；不提交 `.godot/` 缓存。
- 输入动作使用 `world_` 前缀；全局对象、音频总线及共用资源迁入时统一登记。
- 发起战斗时提供遭遇／敌人 ID、当前角色 ID 和返回上下文。玩家位置、朝向、地图标识及遭遇触发保护由世界侧保存，不把地图节点交给战斗修改。
- 主项目负责角色进度、永久配方发现及世界持久状态；两个原型中的测试存档不能直接当成正式共享存档。
- 当前角色与配方只约定稳定 ID 和数据含义，不提前搭通用共享框架。确有共享代码时确定单一维护来源与同步版本。
- 首次整合可先以其中一个项目为临时宿主；正式主项目归属在接通试验时确定，不额外长期维护第三套独立实现。
- 模块迁移时带齐依赖和 UID，并合并必要项目设置，不覆盖对方整个 `project.godot`。

## 8. 本轮不做与尚未决定的设计

本轮不制作完整世界、正式章节、14 人角色切换与地图技能、关系成长、双结局、完整任务／经济／奖励、检查点系统或大规模化学机关。样板的目标提示和返回保护只用于验证体验，不作为这些系统的正式实现。

正式版允许探索切换已解锁角色、角色影响环境等方向继续保留；具体技能、线索如何影响配方开放、战前换人、败北回退和检查点语义仍按总文档待定项处理。不得通过样板临时行为静默决定这些规则。

## 9. 后续维护

每次试验记录构建、镜头／渲染参数、资产版本、截图及性能环境。保留有价值的对照，明确当前采用方案和遗留问题。规则变化回到统一总文档登记，技术试验结论在本项目更新；本文不是要求现在补写完整世界设计。
