# TCA 战斗原型｜基础说明

版本：v0.1　日期：2026-10-25　阶段：Pre-production／Prototype 0

本文确定本子项目的目标、设计来源、范围及整合边界。它是开发入口，不替代总纲，不将待批配置视为已批准，也不代表项目已经实现或通过测试。

## 1. 本项目要做什么

制作一个能独立启动、打完、重开，并有清楚音画反馈的单角色 PvE 卡牌战斗原型。用氧 O 的元素牌、真实化学配方与有限资源「叠」，验证三件事：玩家能否理解合成、是否作出有意义的资源和时机选择、是否愿意重复尝试不同打法。

原型目标单场 3～5 分钟，属于待实测目标；正式版普通战斗 5～10 分钟的目标不因此改变。正确结算是前提，玩法价值还须通过实际试玩判断。

## 3. 已确认的实施边界

- 只操作氧 O 一个角色，对抗一个采用固定行动循环、公开下一行动意图的测试敌人。
- 初始牌组 10 张真实实例：O×4、H/C/N 各×1、固定招牌化合物×1、招牌单质×2。招牌不能作为合成材料。
- 起手恰好 5 张，固定化合物与两种不同元素保底来自真实牌组实例；具体优先组合仍按待批配置管理。
- 玩家先手，可以连续执行合法行动并主动结束；普通 PvE 不设置固定 60 秒倒计时。
- 标准实验初始 35 叠，无额外补充；每种必需元素至少投入一张真实元素牌，实牌与叠精确补足计量。
- 同时提供手动合成和已知配方快捷合成，共用一套合法性、计量与提交逻辑。
- 预览／取消不扣真实资源；合成提交须完整成功或完全不生效，成功只生成一张产物卡。
- 初始牌和消耗的元素牌可进入弃牌与回洗；本场生成产物使用后移除。相同卡名不能掩盖不同来源。
- 成功生成产物才登记正式配方发现；首次发现需持久化、可恢复，并避免重复记账。
- 共同回合末状态、抽牌和能量回复遵守总文档；首共同回合不额外回能，缺牌不判负。
- 数值护盾不自然回合清空；多段伤害使用独立 DamageEvent；P0 抗性阶段首轮恒等处理。
- 治疗、Buff、Debuff、护盾、资源变化、抽牌、伤害采用第二部分 §6.2 的测试顺序。终局检查的不同粒度须对照第一部分 §05.3 与第二部分 §6.2.1，遇到影响实现的歧义先记录并明确口径，不自行改变正式规则。
- HP 终局、同死、认输及 100 共同回合平局必须覆盖；第 100 回合采用第二部分 §6.2.4 的阶段性语义。

## 4. 开工配置与仍待关闭的事项

| 事项 | 当前状态／处理方式 |
|---|---|
| 氧定位、10 张牌结构、敌人循环与意图 | 已确认结构 |
| 氧属性、具体牌名／费用／效果 | 第二部分 §2 的 Baseline A 提案，待批准后作为首轮配置 |
| 首批 H₂O、H₂O₂、CO₂、NO | 建议首批集合；外部证据初核不等于项目正式科学／内容审核及开放批准 |
| 测试敌人 HP、伤害、护盾 | 第二部分 §5 的待批配置，不能把 30／40 等讨论值当成正式值 |
| 起手组合优先级、输入细节 | 按原文状态处理，开发前确定必要口径 |
| 写盘失败、断电、重试恢复 | 在持久化实现中落实策略和验收证据 |

数值配置应有版本号；获批后的平衡调整通过配置迭代，不必先追求最终平衡。允许使用明确标识的开发夹具检查工程行为，但夹具不得冒充已审核可执行内容或有效玩法验收样本。

## 5. 交付顺序与完成标准

| 阶段 | 应得到的可运行成果 | 完成标准 |
|---|---|---|
| M1 第一场像游戏的战斗 | 卡组、起手、出牌、抽牌回洗、能量、HP／护盾、敌人意图和胜负 | 可从启动打到结束并重开；出牌、命中、护盾和胜负具备基础动效与音效 |
| M2 合成核心瞬间 | 手动预览、35 叠支付、获批首批配方、产物、快捷合成和多段伤害 | 从选材料到产物释放可完整游玩；取消无损、提交不重扣；合成有辨识度的反馈 |
| M3 可重复闭环 | 最小状态、回合末结算、发现存档、同种子／新种子重开、日志 | 重启保留发现，关键牌序可复现，非法操作与失败路径不会破坏状态 |
| M4 测试就绪 | 节奏、可读性、数值与表现打磨 | 总文档 F-01～F-12 有可核验证据，内部重复试玩后记录 Gate 结论 |

重点自动验证计量／事务、卡来源与回洗、状态时序、终局、随机复现及存档恢复；表现、理解与重复价值由实际游玩验证。不得将自动测试通过等同于体验通过。

核心表现覆盖合成、出牌、命中、护盾、首次发现与胜负。可用程序图形、Tween、Shader、粒子及基础音效实现；不等待正式资产，也不将其统一推迟到 M4。

## 6. 工程基础与资源

- 统一 Godot 4.6.2 stable、GDScript、Forward+，与探索原型保持一致；这是当前开发基线，不是最终最低硬件承诺。
- 场景、脚本、卡牌配置、专属字体／图像／音效按模块组织在 `res://battle/` 下，迁入主项目保持路径。
- 独立启动与测试辅助放 `res://prototype/`，避免正式模块依赖测试菜单或测试全局对象。
- 使用 Git 管理源码、配置、资源和相关 `.uid` 文件；不提交 `.godot/` 等生成缓存。
- 权威规则独立于 UI 和动画；敌人策略选择合法动作，不能直接改 HP／能量等状态。避免为未批准未来系统预建通用框架。
- 当前两个子项目尚无共享代码库；出现真实共用需求后确定单一维护来源与同步版本，避免双方分别维护角色和配方定义。

视觉来源：[已选白底几何卡面](../TCA_ID/05_视觉参考/卡面使用基准_v1.0_2026-10-24.md)、[氧角色初始版本](../TCA_ID/02_角色/氧_角色初始版本_v1.0.md)。旧卡图内嵌数值须核对；视觉获批不代表战斗数据已获批。

## 7. 与探索及主项目的整合约定

以下是本次开发约定，不是新增正式玩法：

- 战斗通过明确数据入口接收角色 ID、敌人／遭遇 ID、配置版本、随机种子、已发现配方；不直接读取地图节点。
- 结束后返回胜负／平局／认输原因、本场新增发现和必要测试记录。世界奖励、任务推进与地图位置由主项目处理。
- 独立原型可使用自己的测试存档；整合时由主项目统一负责永久发现的可靠保存，战斗成功发现后及时提交，不能仅等战斗结束才保存。
- 输入动作使用 `battle_` 前缀；全局对象、音频总线和共用资源迁入前统一登记，避免同名冲突。
- M1 能打完且探索能移动后安排首次整合冒烟：接触测试敌人→进入战斗→结束→回到原位置；新增配方持久化在 M3 后补齐跨场景检查。
- 整合以迁入模块及补齐项目设置进行，不覆盖整个 `project.godot`，不复制生成缓存。

## 8. 本轮不做

主世界、完整剧情、关系成长、14 人量产、全配方库、复杂 Boss、多目标战斗、复杂抗性／暴击／穿透／反伤／递归被动、外部 AI、联网及完整构筑编辑器均不属于 P0。已知抗性扩展接口可以保留；核心反馈、存档正确性和可复现性属于本轮必需。
